## 0. 要回答的問題

1. 專案宣稱比較五種選樣策略，目前只做了 random、entropy、margin。core-set 與 hybrid 在同一資料、同一 recipe、規則 B 下，對 random 的配對優勢是否成立。
2. 與 v0.2.1 的 entropy／margin 並列（跨實驗參照，不配對）。
3. 明確列出目前還不能宣稱什麼。

不做的事：不調 k-center 或 hybrid 的任何常數；不調任何超參數；不用 test 做任何選擇；不跑規則 A；不重跑 v0.2-lite 與 v0.2.1 的任何 fit；不重跑參考基線。

## 1. arm 定義（凍結）

| arm | 定義 |
|---|---|
| `random` | v0.2-lite §5 的凍結序，作為實驗內對照 |
| `coreset` | 貪婪 k-center。向量：DINOv2-small（`facebook/dinov2-small`，revision `ed25f3a31f01632728cabb09d1542f84ab7b0056`，本機快照）最後層 LayerNorm 後的 CLS 向量，384 維、float32、L2 正規化。距離：cosine 距離 `1 − ⟨u, v⟩`，夾在 `[0, 2]`。初始中心：該輪開始時已標註的全部影像（含 46 張共享起點）。每步選「到最近中心的距離最大」的未標註候選，加入中心後更新距離，直到湊滿當輪的 `b` 張。平手依 `item_id` 升冪。 |
| `hybrid` | 先用當輪 checkpoint 的 entropy 影像分數（與 v0.2-lite 的 `entropy` arm 相同的分數）由高到低排序，取前 `min(5b, 剩餘 pool)` 為候選（分數平手依 `item_id` 升冪），再對候選跑與 `coreset` 完全相同的 k-center。係數 5 凍結。 |

執行細節：k-center 以 float32 在 CPU 上計算（torch），逐候選直接計算距離；不採用 v0.1 §7.4 的 4,096 分塊 CUDA 規範（那是為大池設計的，2,255 張不需要），但語義、平手規則、夾取規則相同，並以最直白的參考實作做等價測試（玩具矩陣上輸出的 id 序列逐字相同）。

embedding 只算一次：對 pool 全部 2,255 張，用快照的前處理設定（短邊 256、中心裁 224、ImageNet 均值與標準差），輸出 `embeddings-dinov2-small.npz`（`item_ids`、`embeddings[N, 384]`）與 `embeddings-receipt.json`（manifest 雜湊、`config.json`／`model.safetensors`／`preprocessor_config.json` 的 SHA-256、revision、張數、npz 的 SHA-256）。`item_id` 是影像位元組的 SHA-256，向量因此綁到影像。test 不算 embedding。encoder 不微調。

## 3. 預先固定的指標與判定

| 項目 | 值 |
|---|---|
| 主要指標 | 每 seed 的配對 nAUBC 差：`coreset − random`、`hybrid − random`，同一次實驗內（同一個 2% fit） |
| 次要指標 | 20% 的 mAP50–95 配對差；20% 最低類別 recall（只報範圍）；20% 佔同 seed 規則 B 參考基線的比例；每設定實際揭露的影像／框／負樣本數 |
| 跨實驗參照 | v0.2.1 的 entropy／margin 曲線與配對差並列呈現，標明「不同實驗、不同 2% fit，不配對」 |
| 記錄 | ledger 的 `score` 對 `coreset`／`hybrid` 記選中時的 k-center 距離；`hybrid` 每輪另存完整候選清單（id 與 entropy 分數）到 `hybrid-shortlists.json`；實驗收據記 `embeddings_sha256`；fit 收據欄位同 v0.2.1 |

判定規則（寫在看結果之前）：

- 「core-set 一致優於 random」成立的條件：規則 B 下 `coreset − random` 的配對 nAUBC 差在 3 個 seed 都為正。`hybrid` 同樣分開判定。
- 只要有任一 seed 為負，就寫「不一致」，不用平均值救回。
- 不對差的量值設門檻；報告時把 seed 43 的兩次同 seed 重播（audit 文件）當量值尺度引用。
- 三個 seed 的最大／最小只稱為**範圍**，不是信賴區間；n = 3 不做區間估計。
- 最低類別 recall 只報範圍；v0.2.1 已顯示它的區間分離與訓練規則有關，本輪不用它下任何結論。
- core-set 預期會比 random 揭露更多負樣本（多樣性偏好覆蓋整個影像分布，而 pool 有 62% 負樣本），這要照實報，不解釋成優點或缺點。
- 不宣稱降低人工標註成本（沒有量測標註時間）；不宣稱 deterministic 或跨機可重現。embedding 前向本身不保證位元相同，但選樣以存檔的 npz 為準，可從磁碟重算核對。

## 4. 執行順序

1. **CPU**：`lite/diversity.py`（embedding、k-center、hybrid）、`REGISTERED_ARMS` 加兩個 arm、`rounds.next_acquisition` 接 embedding、`experiment.py` 的 hybrid 打分與收據欄位、`val lite embed` 命令、啟動器 `-Arms`／`-Embeddings`、新的核對腳本（含從 npz 與 ledger 重算選圖序列）；全部有測試；設 `VAL_DINOV2_SNAPSHOT` 時用真模型在 CPU 跑 embedding 整合測試。
2. **embedding**：`val lite embed` 一次（GPU 空閒時約 1 分鐘；CPU 約 5 分鐘）。產出放 `lite\data\czech\`。
3. **Pilot（GPU，seed 17）**：啟動器 `-Rule fixed-epochs -Arms random,coreset,hybrid -Embeddings <npz>`：2% 基線 → gate → 完整實驗（10 個 fit）。任一步不過就停，回到本文件修訂。
4. **磁碟核對**：v0.2.1 那套（雜湊、步數、warning、ledger 巢狀）加上選圖重算逐字相同。
5. **多 seed（GPU）**：seed 29、43，一次一條，前一條核對通過才下一條。
6. **彙總**：`val lite summarize` 三份實驗收據，附規則 B 的三個參考基線，輸出到新目錄 `docs/results/summary-ep18-div-3seeds/`；不覆寫任何既有 summary。
7. **結果文件**：`docs/results/<日期>-v0.3-diversity.md`，內容依 §5；更新 README 現況段；commit；push 由 owner 決定。

GPU 使用邊界同前：啟動前確認 `nvidia-smi` 無其他工作；不終止、不暫停其他工作；GPU 忙碌時只做 CPU 工作；不 push、不公開資料、不發布權重、不覆寫舊證據。

估計計算量（以 v0.2.1 實測：每 seed 10 個 fit 含打分與評估 44 到 53 分鐘）：三 seed 約 2.5 到 3 小時 GPU，加 embedding 數分鐘；k-center 在 CPU 上每輪數秒。實際秒數以收據為準。

## 5. 結果文件必須包含

絕對表現（每 arm × 預算 × seed 的 mAP50–95）、配對差（每 seed）、最低類別 recall 的範圍、每個設定實際揭露的影像數與框數（含負樣本數）、每個 fit 的步數與秒數、20% 相對參考基線的比例、與 v0.2.1 entropy／margin 的並列（標明不配對）、「還不能宣稱什麼」一節。

## 6. 不在範圍

規則 A 下的 core-set／hybrid、40% 預算、其他國別、其他 encoder、hybrid 的候選改用 margin、任何超參數搜尋、溫度校準、標註時間量測、v0.1 §10.4 的目標成本審查表、Docker、A11。
